\chapter{Requirements Definition}
\label{chap:requirements_definition}

This chapter summarizes the key requirements extracted from the Software Requirements Specification (SRS) for the Quiz Web App (Version 1.0, hereafter referred to as SRS\_updated) \cite{srs_quiz_app}. These requirements are fundamental drivers for the architectural decisions made in this document. Each requirement listed here will be given a unique identifier specific to this Architecture Design Document (ADD).

\section{Functional Requirements (FR)}
\label{sec:functional_requirements}
The Quiz Web App will provide the following core functionalities, as detailed in Section 3 of SRS\_updated.

\begin{itemize}
    \item \textbf{FR1: User Authentication and Authorization}
    \begin{itemize}
        \item \textbf{FR1.1:} The system shall allow new users to register by providing a username, password, and email.
        \item \textbf{FR1.2:} User passwords shall be at least 8 characters long and include at least one number and one special character.
        \item \textbf{FR1.3:} The system shall validate that the repeated password matches the password during registration.
        \item \textbf{FR1.4:} Upon successful registration, the user shall be logged in, and an authentication token shall be issued.
        \item \textbf{FR1.5:} Newly registered users shall be assigned the 'user' role by default.
        \item \textbf{FR1.6:} The system shall allow registered users to log in using their username and password.
        \item \textbf{FR1.7:} Upon successful login, the system shall issue an authentication token (JWT).
        \item \textbf{FR1.8:} The system shall display an error message for incorrect username or password.
        \item \textbf{FR1.9:} The system shall allow authenticated users to log out.
        \item \textbf{FR1.10:} Upon logout, the session token shall be invalidated/cleared on the client-side.
        \item \textbf{FR1.11:} The system shall use token-based authentication for API requests.
        \item \textbf{FR1.12:} Authentication tokens shall have an expiration time (e.g., 1 hour).
        \item \textbf{FR1.13:} The system shall handle expired tokens, prompting re-login if necessary.
        \item \textbf{FR1.14:} The system shall restrict access to administrative functions to users with the 'admin' role.
        \item \textbf{FR1.15:} Users with the 'user' role shall not be able to access administrative functionalities.
        \item \textbf{FR1.16:} User passwords shall be stored in a hashed format using bcrypt.
        \item \textbf{FR1.17:} The system shall use route guards (AuthGuard) to protect routes requiring authentication.
        \item \textbf{FR1.18:} The system shall use route guards (InvAuthGuard) to restrict access to authentication pages (login, register) for already authenticated users.
    \end{itemize}

    \item \textbf{FR2: User Profile Management}
    \begin{itemize}
        \item \textbf{FR2.1:} Authenticated users shall be able to view their profile information (username, name, surname, age, email, profile image).
        \item \textbf{FR2.2:} Authenticated users shall be able to edit their name, surname, age, and email. Username and role are not editable by the user through this interface.
        \item \textbf{FR2.3:} The system shall validate email format upon editing profile information.
        \item \textbf{FR2.4:} Authenticated users shall be able to upload a profile image.
        \item \textbf{FR2.5:} The system shall enforce a file size limit for profile images (e.g., 200KB).
        \item \textbf{FR2.6:} Uploaded profile images shall be stored on the server.
        \item \textbf{FR2.7:} Authenticated users shall be able to remove their current profile image.
    \end{itemize}

    \item \textbf{FR3: Quiz Management (Admin)}
    \begin{itemize}
        \item \textbf{FR3.1:} Administrators shall be able to view a list of all quizzes, displaying title, category, number of questions, time limit, and last updated timestamp.
        \item \textbf{FR3.2:} Administrators shall be able to add a new quiz by providing a title, description, category, time limit (optional), and assigning questions.
        \item \textbf{FR3.3:} Input validation shall be performed for quiz details during creation.
        \item \textbf{FR3.4:} Administrators shall be able to edit existing quizzes, including title, description, category, time limit, and assigned questions.
        \item \textbf{FR3.5:} Administrators shall be able to delete quizzes.
        \item \textbf{FR3.6:} Deleting a quiz shall also delete its associated assigned questions.
        \item \textbf{FR3.7:} Administrators shall be able to select and assign existing questions to a quiz when creating or editing a quiz.
        \item \textbf{FR3.8:} A quiz can have a variable number of questions (minimum 3, maximum 9 based on UI constraints for adding questions).
    \end{itemize}

    \item \textbf{FR4: Category Management (Admin)}
    \begin{itemize}
        \item \textbf{FR4.1:} Administrators shall be able to view a list of all quiz categories, displaying name, description, and whether the category is assigned to any quiz.
        \item \textbf{FR4.2:} Administrators shall be able to add a new quiz category by providing a name and description.
        \item \textbf{FR4.3:} Input validation shall be performed for category details during creation.
        \item \textbf{FR4.4:} Administrators shall be able to edit existing quiz categories (name, description).
        \item \textbf{FR4.5:} Administrators shall be able to delete a quiz category.
        \item \textbf{FR4.6:} A category cannot be deleted if it is currently assigned to any quiz. A tooltip shall indicate which quizzes are using the category.
        \item \textbf{FR4.7:} Categories shall be associated with a color and an image for display purposes (assigned dynamically by the QuizService).
    \end{itemize}

    \item \textbf{FR5: Question Management (Admin)}
    \begin{itemize}
        \item \textbf{FR5.1:} Administrators shall be able to view a list of all questions, displaying the question text, last modified timestamp, and whether the question is assigned to any quiz.
        \item \textbf{FR5.2:} Administrators shall be able to view the details of a question, including its options and correct answer, by toggling a details view.
        \item \textbf{FR5.3:} Administrators shall be able to add a new question by providing the question text, multiple options (minimum 3, maximum 5 based on UI), and selecting the correct answer from the options.
        \item \textbf{FR5.4:} Input validation shall be performed for question details during creation.
        \item \textbf{FR5.5:} Administrators shall be able to edit existing questions, including text, options, and the correct answer.
        \item \textbf{FR5.6:} Administrators shall be able to delete a question.
        \item \textbf{FR5.7:} A question cannot be deleted if it is currently assigned to any quiz. A tooltip shall indicate which quizzes are using the question.
        \item \textbf{FR5.8:} Administrators shall be able to generate new questions using the OpenAI API by specifying a category and the number of desired answers (3-6).
        \item \textbf{FR5.9:} Generated questions from OpenAI shall be automatically added to the system.
    \end{itemize}

    \item \textbf{FR6: User Management (Admin)}
    \begin{itemize}
        \item \textbf{FR6.1:} Administrators shall be able to view a list of all registered users, displaying username, name, surname, age, and role.
        \item \textbf{FR6.2:} Administrators shall be able to add a new user by providing a username, password, and role.
        \item \textbf{FR6.3:} Administrators shall be able to change the role of a user (e.g., from 'user' to 'admin' or vice-versa).
        \item \textbf{FR6.4:} Administrators shall not be able to change their own role.
        \item \textbf{FR6.5:} Administrators shall be able to delete users.
        \item \textbf{FR6.6:} Administrators shall not be able to delete their own account.
    \end{itemize}

    \item \textbf{FR7: Quiz Taking}
    \begin{itemize}
        \item \textbf{FR7.1:} All users (registered and anonymous) shall be able to view a dashboard of available quizzes.
        \item \textbf{FR7.2:} Quizzes on the dashboard shall display title, category, number of questions, time limit, and last updated timestamp.
        \item \textbf{FR7.3:} Users shall be able to filter quizzes by category and search by title on the dashboard.
        \item \textbf{FR7.4:} Authenticated users shall be able to start a selected quiz.
        \item \textbf{FR7.5:} Anonymous users attempting to start a quiz shall be prompted to log in.
        \item \textbf{FR7.6:} During a quiz, one question shall be displayed at a time with its multiple-choice options.
        \item \textbf{FR7.7:} Users shall select one answer for each question.
        \item \textbf{FR7.8:} The quiz interface shall display the current question number and the total number of questions.
        \item \textbf{FR7.9:} If a quiz has a time limit, a countdown timer shall be displayed.
        \item \textbf{FR7.10:} If the time expires, the quiz shall end automatically.
        \item \textbf{FR7.11:} The timer state (timeLeft) shall be preserved in session storage to prevent refresh from restarting the timer.
        \item \textbf{FR7.12:} Users shall confirm their answer for each question to proceed to the next.
        \item \textbf{FR7.13:} Upon completing all questions or if time expires, the quiz shall end.
        \item \textbf{FR7.14:} The system shall display the user's score (number of correct answers) and total questions upon completion.
        \item \textbf{FR7.15:} If the quiz was timed, the remaining time shall be displayed upon completion.
        \item \textbf{FR7.16:} Quiz results (user ID, quiz ID, score, total questions, questions answered, timestamp) shall be stored in the database.
        \item \textbf{FR7.17:} During a quiz, users shall be able to request a hint for the current question via the OpenAI API.
    \end{itemize}

    \item \textbf{FR8: Leaderboard}
    \begin{itemize}
        \item \textbf{FR8.1:} All users (registered and anonymous) shall be able to view the leaderboard.
        \item \textbf{FR8.2:} The leaderboard shall display user statistics including username, age, total quizzes taken, total questions answered, total score, and average score percentage.
        \item \textbf{FR8.3:} User profile images shall be displayed next to their usernames on the leaderboard.
        \item \textbf{FR8.4:} Users shall be able to sort the leaderboard by username, age, total quizzes, total questions, total score, and average score.
        \item \textbf{FR8.5:} Sorting on the leaderboard shall support ascending and descending order.
    \end{itemize}

    \item \textbf{FR9: OpenAI Integration}
    \begin{itemize}
        \item \textbf{FR9.1:} The system shall interface with the OpenAI API to generate new quiz questions based on a specified category and number of answers (for admins).
        \item \textbf{FR9.2:} The generated questions shall be parsable and storable in the application's question format.
        \item \textbf{FR9.3:} The system shall interface with the OpenAI API to provide hints to users for quiz questions (during quiz taking).
    \end{itemize}
\end{itemize}

\section{Non-functional Requirements (NFR)}
\label{sec:non_functional_requirements}
The system must adhere to the following non-functional requirements, which significantly influence the architectural design, as detailed in Section 5 of SRS\_updated.

\subsection{NFR1: Performance Requirements}
\begin{itemize}
    \item \textbf{NFR1.1: Response Time:} API responses should ideally be within a reasonable timeframe (e.g., < 2 seconds for most operations). OpenAI API calls might take longer depending on the external service.
    \item \textbf{NFR1.2: Preloading:} Lazy-loaded Angular modules specified with `preload: true` in `app-routing.module.ts` shall be preloaded to improve perceived performance.
\end{itemize}

\subsection{NFR2: Security Requirements}
\begin{itemize}
    \item \textbf{NFR2.1: Authentication Mechanisms:} Secure user authentication using tokens (JWT) and hashed passwords (bcrypt) shall be implemented.
    \item \textbf{NFR2.2: Authorization Control:} Role-based access control shall be enforced to protect administrative functionalities.
    \item \textbf{NFR2.3: Input Validation:} All user inputs shall be validated on both client-side and server-side to prevent common vulnerabilities. (Note: SRS\_updated 2.5 mentions "Weak backend checks (if any)" as a limitation, which this NFR aims to address by mandating robust server-side validation).
    \item \textbf{NFR2.4: API Security:} API endpoints requiring authentication shall be protected and only accessible with a valid token.
    \item \textbf{NFR2.5: Secrets Management:} Sensitive information like API keys (OpenAI) and database connection strings shall be managed through environment variables and not hardcoded.
    \item \textbf{NFR2.6: Secure Communication:} In a production environment, all communication between client and server, and server to external APIs, shall occur over HTTPS.
\end{itemize}

\subsection{NFR3: Usability Requirements}
\begin{itemize}
    \item \textbf{NFR3.1: Learnability:} The application should be intuitive and easy to learn for new users of all classes (Anonymous, Registered, Admin).
    \item \textbf{NFR3.2: Efficiency:} Users should be able to perform tasks (taking quizzes, managing content) efficiently with minimal steps.
    \item \textbf{NFR3.3: Error Prevention and Messaging:} The system should provide clear, user-friendly error messages and input validation to help users avoid and correct mistakes.
    \item \textbf{NFR3.4: Responsiveness (UI):} The UI shall be responsive and adapt to various screen sizes (desktop, tablet, mobile).
\end{itemize}

\subsection{NFR4: Maintainability}
\begin{itemize}
    \item \textbf{NFR4.1: Modularity:} The application shall be structured into well-defined modules (e.g., Angular modules, backend route/service separation) to promote separation of concerns and ease of modification.
    \item \textbf{NFR4.2: Code Readability:} Code should follow consistent styling and commenting practices to be understandable by developers (assumed).
    \item \textbf{NFR4.3: Configuration Management:} Application configuration (DB strings, API keys, ports, API URLs) shall be managed through environment variables (`.env` files for backend, Angular environment files for frontend).
\end{itemize}

\subsection{NFR5: Portability}
\begin{itemize}
    \item \textbf{NFR5.1: Browser Compatibility:} The frontend application should be compatible with modern web browsers (e.g., Chrome, Firefox, Safari, Edge).
    \item \textbf{NFR5.2: Dockerization:} The application (frontend, backend, MongoDB) shall be containerized using Docker and orchestrated with `docker-compose.yml` to facilitate deployment across different environments.
\end{itemize}

\subsection{NFR6: Reliability}
\begin{itemize}
    \item \textbf{NFR6.1: Data Integrity:} Data stored in the MongoDB database should maintain its accuracy and consistency.
    \item \textbf{NFR6.2: Error Handling:} The application should gracefully handle runtime errors and external service failures (e.g., OpenAI API unavailability), providing informative messages to the user or logging them appropriately for administrators.
\end{itemize}

\subsection{NFR7: Deployment Requirements}
\begin{itemize}
    \item \textbf{NFR7.1: Local Deployment Support:} The application must be deployable locally using `npm install` and `ng build` as per README instructions.
    \item \textbf{NFR7.2: Dockerized Deployment:} The application must be deployable using the provided `docker-compose.yml` file for frontend, backend, and MongoDB services.
    \item \textbf{NFR7.3: Cloud Deployment Suitability:} The architecture should be suitable for deployment to cloud platforms like Azure (as demonstrated by the existing Azure deployment).
    \item \textbf{NFR7.4: Production Build Optimizations:} The Angular frontend shall have a production build configuration with optimizations.
\end{itemize}

\subsection{NFR8: Design and Implementation Constraints}
These are explicit constraints from the SRS that the architecture must incorporate.
\begin{itemize}
    \item \textbf{NFR8.1: Frontend Technology Stack:} Angular framework (version \^19.2.6) with TypeScript (version 5.5.4). Must use Angular routing, services, pipes. UI with Bootstrap and Angular Material.
    \item \textbf{NFR8.2: Backend Technology Stack:} Node.js with Express framework.
    \item \textbf{NFR8.3: Database Technology:} MongoDB. At least three entities (Quizzes, Categories, Questions) besides users must be managed.
    \item \textbf{NFR8.4: Authentication Mechanism:} JWT-based authentication with bcrypt for password hashing.
    \item \textbf{NFR8.5: API Design:} RESTful API for client-server communication.
    \item \textbf{NFR8.6: OpenAI API Integration:} Must use OpenAI API (gpt-3.5-turbo model) for hints and question generation.
    \item \textbf{NFR8.7: Deployment Containerization:} Docker and `docker-compose.yml` must be used.
    \item \textbf{NFR8.8: Core Technology Mandate (MEAN Stack):} The project must adhere to the MEAN (MongoDB, Express, Angular, Node.js) stack.
\end{itemize}
